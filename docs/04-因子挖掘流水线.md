# 因子挖掘流水线（真实数据）

合成市场用来验证机制，真实数据才能挖出真因子。但接上真实数据的那一刻，
三类合成数据里完全不存在的问题会同时出现 —— 而且它们都不报错。

---

## 一、Point-in-time：最贵的一课

### 三个必须处理的坑

**1. 公告日 ≠ 报告期**

2023 年三季报的报告期是 `2023-09-30`，公告日可能是 `2023-10-28`。
在 10-28 之前市场不知道这份报表。按报告期对齐 = 提前一个月知道业绩。

**2. 利润表和现金流量表是累计值（YTD）**

一季报的"净利润"是 Q1 的，中报是 Q1+Q2，三季报是 Q1+Q2+Q3。
直接拿来算 TTM 会得到荒谬的数字。必须先累计转单季：

```
Q1单季 = Q1累计
Q2单季 = H1累计 − Q1累计
Q3单季 = Q3累计 − H1累计
Q4单季 = 年报累计 − Q3累计
TTM   = 最近四个单季之和
```

资产负债表是**时点值**，不需要转换。两类字段必须分开处理
（`fundamentals.FIELD_KIND` 做这个区分）。

**3. 追溯调整（restatement）**

同一报告期会被多次公告，后一次修正前一次。PIT 的定义是"T 时刻你所知道的值"，
必须取 `ann_date <= T` 的最新那一版，而不是数据库里的最终版。
用最终版 = 提前知道了会计差错更正。

### 实测：搞错 PIT 的代价

用同一个业绩增速因子，三种对齐方式（40 日前瞻，窗口覆盖公告日）：

| 对齐方式 | IC 均值 | 年化 ICIR | 多空年化 |
|---|---|---|---|
| A. 正确 PIT（按公告日） | −0.0181 | **−0.92** | −1.26% |
| B. 报告期对齐（常见错误） | +0.0058 | **+0.27** | +1.08% |
| C. 最终版追溯（隐蔽错误） | −0.0164 | −0.82 | −2.25% |

**最该注意的不是那 2.3pp 收益差，是 ICIR 的符号翻转。**
一个真实有害的因子（ICIR −0.92），仅因为对齐方式错误就变成了看起来可用（+0.27），
足以通过初筛进入你的组合。

一个重要的诚实限定：PIT 错误的伤害大小取决于因子对**公告事件**的敏感度。
E/P 这类水平值因子受影响小；增速、超预期类因子受影响大 —— 而后者极其常用。
另外本演示中的追溯调整是随机的（均值 1.0），真实世界的会计差错更正常与
后续暴雷相关，方向不随机，真实偏差会比这里更大。

### 用法

```python
from artemis.data.fundamentals import align_to_bars, staleness_days

fund = align_to_bars(pit_long_table, bars,
                     fields=["net_profit", "revenue", "total_equity"],
                     min_report_lag_days=1)   # 额外缓冲，防数据源公告日不准
roe = fund["net_profit"] / fund["total_equity"]

# 监控数据陈旧度：4 月初用的还是去年三季报，已陈旧 180+ 天
stale = staleness_days(pit_long_table, bars, "net_profit")
```

财务长表必须含 `code / report_period / ann_date / field / value` 五列。
**缺 `ann_date` 的数据一律拒收** —— 没有公告日就无法做 PIT，
`validate_pit()` 会直接抛错而不是猜一个。

数据源提示：AkShare 的 `stock_yjbb_em` / `stock_lrb_em` 带"最新公告日期"；
Tushare 的 `income` / `balancesheet` 带 `ann_date` 和 `f_ann_date`（后者是实际披露日）。

## 二、挖掘就是大规模多重检验

### 问题的规模

你测 500 个因子，用 p<0.05 筛选。即使所有因子真实无效，也会有约 25 个"显著"。
你挑出它们做成组合，回测漂亮，上实盘归零。这不是运气差，是统计学的必然。

实测对照（200 个候选，其中 10 个真有效）：

| 筛选方式 | 入选 | 真阳性 | 假阳性 | 实际假阳率 |
|---|---|---|---|---|
| 朴素 p<0.05 | 21 | 10 | **11** | **52%** |
| BH FDR(10%) | 2 | 2 | 0 | **0%** |

FDR 的代价是召回率下降（10 个真因子只找回 2 个）。在真金白银的场景下，
这个取舍是对的：漏掉一个好因子只是没赚到，选中一个假因子是真亏。

### 三道防线

**1. 增量价值检验（最容易被忽略，也最有价值）**

新因子对已有因子库做逐日截面回归，看残差还剩多少 IC。
`retention = resid_icir / raw_icir`，低于 50% 判定冗余。

实测中 7 个 |t| > 7 的"强因子"被这一关拦下：

| 因子 | ICIR | t 值 | 保留率 | 判定 |
|---|---|---|---|---|
| reversal_15 | −1.85 | −9.30 | **1%** | 冗余（就是 reversal_20） |
| reversal_25 | −1.85 | −9.31 | **0%** | 冗余 |
| ma_ratio_5_20 | +2.08 | +10.47 | 31% | 冗余 |
| close_position_20 | +1.48 | +7.46 | **−2%** | 冗余 |

没有这一关，你会"发现"七个漂亮因子，然后把同一个赌注下七遍 ——
回测夏普虚高，实盘回撤翻倍。

**2. FDR 控制（Benjamini-Hochberg）**

控制的是"入选批次里假阳性的占比"，而不是单个因子的 p 值。
关键纪律：FDR 必须基于**完整的搜索空间**计算，不能只拿好看的那几个来算。

**3. Harvey-Liu-Zhu 门槛**

学术界已发表 300+ 因子。考虑发表偏差和数据挖掘，新因子的 t 值门槛
应该是 **3.0** 而不是 2.0。散户的搜索空间不比学术界小，门槛只该更高。

实测中 `noise_control_2` 拿到 t=1.88、p=0.060 —— 朴素标准下算"边缘显著"，
HLZ 门槛下干脆利落地否决。

## 三、研究日志：让"试了多少次"变成可审计事实

上面三道防线全都依赖一个数字：**你到底试过多少次**。
而人记不住，更关键的是人**不愿意**记住 —— 调参调了三天，最后只记得成功那次。

所以 `ResearchLog` 自动记录每次评估，不管结果好坏。它还按**公式指纹**去重，
识破"换个名字重测同一个因子"。

### 独立性的坑

DSR 假设各次试验相互独立。但挖掘时你会测一堆近亲因子，它们的 ICIR 高度相关，
会把 `sigma_SR` 抬得虚高，进而把运气门槛抬到不合理的位置。

实测对比（同一批 14 次试验）：

| | 含冗余试验 | 剔除冗余后 |
|---|---|---|
| 用于估计的试验数 | 14 | 7 |
| sigma_SR | 1.313 | **0.595** |
| 运气可解释的 ICIR | 2.282 | **1.034** |
| 最优因子 ICIR | 2.083（冗余因子） | 1.449（真候选） |
| DSR 判定 | 不通过 | **警戒** |

所以 `multiple_testing_penalty()` 的规则是：
**sigma_SR 只用非冗余试验估计，试验次数仍用全量** ——
你确实搜索过那么大的空间，这份惩罚跑不掉。

## 四、真实数据的规模化落地

朴素的 `for code in codes: fetch(code)` 在真实规模下不可用：
5000 只 × 10 年要跑十几小时，被限频掐断一次就得重来。

`artemis/data/ingest.py` 解决三件事：

| 能力 | 做法 |
|---|---|
| 增量 | 按 manifest 记录的覆盖范围，只补缺失尾部 |
| 并发限流 | 令牌桶控制真实速率（不是 sleep），默认 4 线程 / 4 req·s⁻¹ |
| 断点续传 | 每批落地并更新清单，失败的股票记录下来自动重试 |

**一个必须注意的坑**：增量判断要按**交易日**而不是日历日。
`end="2024-03-31"` 是周日，最后交易日是 3/29，直接比日历日的话
每只股票每天都会被重新请求 —— 5000 只就是 5000 次无效请求，正好撞在限频上。
`_effective_end()` 处理这件事。

```python
from artemis.data.akshare_source import AkshareSource
from artemis.data.store import BarStore
from artemis.data.ingest import Ingestor

ing = Ingestor(AkshareSource(), BarStore("./data_cache"),
               max_workers=4, rate_per_sec=4)
ing.run(codes, "2016-01-01", "2026-08-01")     # 首次全量，建议过夜
ing.run(codes, "2016-01-01", "2026-08-22")     # 之后每天增量，几分钟
```

## 五、完整流程

```bash
python scripts/demo_pit_impact.py    # 先看清 PIT 错误的代价
python scripts/mine_factors.py       # 挖掘 + 筛选 + 多重检验惩罚
```

```
1. 载入数据 + 排雷            → 确定研究样本
2. 建立"已有因子库"基准       → 新因子必须超越它才有意义
3. 批量检验候选因子           → 每次试验自动写研究日志
4. 联合筛选                   → FDR + HLZ 门槛 + 冗余检验
5. 报告累计多重检验惩罚       → 你一共搜索了多大的空间
6. 存活的因子进上线闸门       → scripts/validate_strategy.py 的五道关
```

注意第 6 步：挖掘阶段的筛选**不能替代**上线闸门。
挖掘筛的是"这个因子有没有信息"，上线闸门筛的是"这个策略能不能赚钱"。
两者用的是不同的证据，都得过。

## 六、AI 在挖掘环节的分工

```
LLM   → 提出假设、写清经济逻辑、给出计算方式的自然语言描述
人    → 把描述翻译成代码（或审核 LLM 写的代码）
数据  → 裁决
```

**为什么不让 LLM 直接生成代码自动跑**：因子代码里最容易出的错是未来函数，
而它不会报错。让未经审核的生成代码进流水线，等于把最危险的一类 bug
交给一个看不见结果的环节。

`copilot/bridge.py` 的 `HypothesisCard.to_checklist()` 产出实现前的确认清单，
五条都是常见翻车点。研究日志记录 `source="llm"`，几个月后
`llm_hit_rate(log)` 会告诉你：AI 提的假设命中率到底比你自己拍脑袋高吗。
诚实的答案可能是"不高" —— 那也是有价值的结论。
