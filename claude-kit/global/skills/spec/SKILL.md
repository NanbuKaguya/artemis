# /spec：先写清楚"做完是什么样"

## 1. 访谈

一次问一到三个问题，直到你能写出规格。先自己读代码，代码里查得到的不要问。优先问这几件：

- 谁用，在什么场景下用？
- 做完之后，用什么检查能证明它对了？要具体到命令、截图或数字。
- 明确不做什么？
- 有什么约束？比如性能、兼容性、不能动的接口。

## 2. 写 SPEC.md

写到项目根目录；已经有就写到 `docs/specs/<短名>.md`。

```markdown
# <标题>

## 目标
一段话。

## 不做
- …

## 验收
每条都是一个能跑的检查：命令 + 期望结果。

## 方案
关键决定和理由，以及被否掉的备选方案。

## 任务
每个任务是一个 M 级改动，能单独验证、单独提交。按顺序编号。

## 风险与未知
```

## 3. 停下来

把 SPEC.md 给用户看，请他改。确认之后，建议他 `/clear` 或开一个新会话，然后说"按 SPEC.md 做任务 1"。

规格在文件里，不在对话里，所以新会话读文件就能接上，不会被这次访谈的上下文拖累。
